# M4 · Автономный магазинный парсер и детерминированный выбор SKU (без ИИ)

Статус: **SPEC LOCKED / IMPLEMENTATION INCOMPLETE**. Зафиксировано 21.10.2026 по требованию владельца. Отдельная часть M4, не подменяет критерии приёмки M2.

## Обязательный пользовательский сценарий

1. Пользователь выбирает магазин России, город/торговую точку или адрес, доступные через законный публичный интерфейс магазина. Никаких принудительных заказов, авторизации роботом, обходов CAPTCHA/антибота.
2. Из недельного меню агрегировать **обезличенные** ингредиенты (категория, продукт, физическое состояние, нужные граммы, допустимые замены), например: `рис сухой 900 г`, `курица сырая 1500 г`, `овощи свежие 2000 г`. Не переносить название бренда из прошлой покупки в запрос.
3. Сделать проверочный проход **одной категории** (пример: курица), затем пройти **весь** обезличенный список; для каждой позиции собирать разные SKU, а не первый найденный.
4. Для каждого кандидата открыть, когда разрешено и доступно, карточку товара; собрать: название, разновидность/сорт, обработка (сырая/приготовленная/замороженная и т.д.), форму/часть туши, **состав**, пищевую маркировку и аллергены, изготовителя/поставщика (различать!), массу нетто/дренированную массу, цену целой упаковки, цену за кг съедобной части, скидку/условия карты, дату/магазин/источник, срок годности/условия хранения, реальные рейтинг/число отзывов и подтверждённое наличие при наличии данных. Пропущенные поля = UNKNOWN, не угадывать.
5. **Детерминированно**, без LLM: нормализация текста → признаки → строгие ограничения → группы эквивалентности → объяснимое ранжирование → совместная оптимизация **всей недели** по целым упаковкам.
6. Выдать внутреннюю корзину FoodPlan AI с выбранными конкретными SKU и альтернативами и причинами выбора («120 ₽ вместо 400 ₽: тот же сорт/масса/состав по подтверждённой карточке»). Не добавлять товары в корзину магазина.
7. Даже при 100 ₽ вернуть правдивую частичную покупку, если доступна, с пометкой дефицита пищи/КБЖУ и без фиктивной семидневной обеспеченности; точный бюджет 100..100000 ₽ с шагом 1 ₽.

## Фильтры (порядок обязателен)

### HARD FAIL: товар исключается
- Подмена вида: куриное филе ≠ тушка, грудка ≠ голень; рис для суши ≠ пропаренный; сырой продукт ≠ готовый. Подмена допустима только при **явном** правиле рецепта/пересчёте съедобного выхода и нутриентов.
- Несовпадение строгих исключений и аллергии; **неизвестный полный состав/аллергенная маркировка при заявленной аллергии → НЕ ПРИНИМАТЬ**.
- Сомнительная единица упаковки: ₽/кг для весового товара ≠ ₽ за упаковку; мл нельзя переводить в граммы без проверенной плотности; масса с рассолом ≠ дренированная масса.
- Неизвестная/устаревшая цена при попытке заявить `fitsBudget=true`; различие адреса/города магазина; явно нет в наличии.
- Невалидные URL (чужой домен, небезопасная схема), дубли и отсутствие однозначного SKU.

### Equivalent for price comparison
- Совпадают конкретный пищевой вид, категория/сорт/технологическое состояние, назначение в рецепте, релевантный состав/характеристики, единица и сравнимый съедобный вес.
- **Разные производители не обязательно означают разное качество.** Производитель сохраняется как атрибут происхождения/прослеживаемости; не штрафовать или премировать за узнаваемость бренда.
- При недостатке состава/сорта/качества нельзя заявлять «совершенно одинаковые». Можно сравнить только известные поля, отметить **EQUIVALENCE_UNKNOWN**.
- Пример 120 ₽ vs 400 ₽: выбирать дешёвый при доказанной эквивалентности и корректной стоимости на требуемое количество; более дорогой допускается только при **доказанном значимом для рецепта** преимуществе.

### SOFT score: ранжирование среди прошедших HARD
- 1) минимальная **полная стоимость нужного числа целых упаковок** с учётом отходов/дренированной массы;
- 2) подтверждённые характеристики: сорт/качество, пищевые показатели, срок годности при наличии;
- 3) отзывы с доверительным сглаживанием, вес по количеству, неизвестный рейтинг = UNKNOWN;
- 4) штраф за лишнюю закупку/потенциальные отходы;
- 5) стабильный tie-breaker `skuId` / канонический URL, чтобы результат не зависел от порядка обхода.
- При большем бюджете разрешены **только обоснованные** апгрейды; тратить потолок целиком не требуется.

## Архитектура без ИИ

`Menu → NormalizedShoppingNeed[] → ScanPlan → RetailerAdapter(store, locality) → SearchCategory → SKUPage → ParsedOffer[] → StrictValidator → EquivalenceGroups → BasketOptimizer → Explanation + Provenance`.

- **RetailerAdapter**: отдельный разрешённый адаптер на магазин; его состояние ENABLED / LIMITED / BLOCKED / UNAVAILABLE. UI может открывать штатный WebView для локального выбора адреса; никакой подделки запроса/авторизации/скрытого обхода защиты.
- **ScanPlan**: один пилотный продукт «курица» → остальные по списку; список категорий фиксируется до обхода; лимит страниц/частоты и дедупликация.
- **Parser**: строгая схема данных, регулярные выражения/таблицы словоформ, JSON/HTML только в рамках разрешённого доступного интерфейса. HTML селекторы версионированы; никакой LLM в рантайме.
- **Evidence**: SKU ID, URL, timestamp, store/city, поля с источниками, снимок/хеш доступной маркировки; конфликты и UNKNOWN в журнал.
- **Engine**: Android Kotlin domain offline, целые копейки, целые упаковки, воспроизводимый расчёт; сбор и кэш отдельно.
- Публично поддерживаемые сети подключать **по одной** после реального proof-of-access. Нельзя обещать полный обход Пятёрочки/Перекрёстка, пока есть JS challenge.

## Обязательный конечный Gauntlet

1. Пилот: курица; доказать адрес/магазин, хотя бы 2 реальные разные SKU, производителя/состав/цену из карточки; отказ при отсутствии данных.
2. Полный обезличенный список ≥30 ингредиентов; собирать множественные альтернативы; логировать **фактически доступные**, недоступные и ошибки по каждой категории.
3. ≥100 реально собранных SKU, отдельная независимая разметка ≥50 пар «эквивалент/неэквивалент/неизвестно» и ≥50 SKU карточек для оценки качества разбора.
4. 100% выбранных SKU имеют однозначную упаковочную цену/единицу/вес; 100% аллергических hard-fail тестов отклоняют опасную/неизвестную маркировку. Ошибки неизвестного свойства **не скрывать**.
5. Семидневные бюджеты 100 / 356 / 2500 / 63218 / 100000 ₽: отсутствие придуманной цены и гарантии полноценного питания; расчет упаковок; запрет превышать бюджет при `fitsBudget=true`.
6. Android JVM unit tests + APK build + Android emulator E2E + внешний по отношению к парсеру эталон карточек/цен для выбранного магазина, в одной зафиксированной версии.
7. Раздельные PASS / FAIL: deterministic logic, adapter network, address-specific price, allergen evidence, full-cart availability, APK, emulator. Нет «M4 PASS» по одним фикстурам.

**Текущий статус на старте:** 37/37 названий каталога имеют правила сопоставления; Magnit WebView извлекает только видимые карточки и не проходит поисковый список сам; состава и производителей из каждой SKU-карточки пока нет; проверки живых адресных цен нет. Не принимать M4 до полного автоматического прохода и независимой проверки.
